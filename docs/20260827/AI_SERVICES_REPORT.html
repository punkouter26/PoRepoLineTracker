What actually costs money

The only metered external dependencies are GitHub's REST API (rate-limited per OAuth token, not billed) and Azure Table Storage (billed per transaction and per GB). Compute is a single App Service instance; the expensive operation is a full-history re-analysis, which is CPU and git I/O, not network.

Tier 2 — Architectural

Tier 2Where an AI service would sit in a system of this shape is between the analysis pipeline and the scoring surfaces. That edge is drawn below as it actually exists: a pure-function boundary with no network hop.

The three “AI-shaped” surfaces, and what they really are

Code Health — /api/code-health/{id}

Six line-oriented proxies scored on fixed weights. Deliberately not Visual Studio's Maintainability Index: that needs Halstead volume and a control-flow graph, meaning a parser per language and a resolved compilation. This app reads blobs across a dozen languages and builds nothing. The ranking is the reliable part; the absolute number is a guide, and the card states this on its face rather than in a tooltip.

Year in Code — /api/recap/{year}

Aggregation over stored commit rows on fixed calendar edges (1 Jan – 31 Dec): peak hour, weekday rhythm, night-owl percent, language drift. Its one genuinely non-obvious figure — drift measured in share, not lines — is arithmetic, not prediction. A type's share can grow while the type shrinks, because everything else shrank faster.

Contributor share — /{id}/contributors/{days}

Percentage of total lines, weighted by lines added rather than averaged per commit — a one-line commit and a 2,000-line refactor are not the same event. Pure division over stored LinesAdded values.

// Weighted mean, then a letter grade
report.Score = (int)Math.Round(
    factors.Sum(f => f.Score * (double)f.Weight) / factors.Sum(f => f.Weight));
report.Grade = GradeFor(report.Score);

Two properties are load-bearing and easy to lose in a refactor. Measuring and judging are separate types — CodeMetricsAnalyzer counts, CodeHealthScoring judges — so re-weighting the report cannot change what was counted. And nesting is the 90th-percentile line depth, not the maximum: one wrapped argument list is indented far past the structure around it, and using the max let a 40-line middleware holding a wrapped CSS string measure 14 levels deep and outrank genuinely tangled files.

public sealed class CodeHealthFactorDto
{
    public string Key  { get; set; } = string.Empty;  // complexity | nesting | file-size |

Measurement and Explanation exist so the score is never presented as an oracle: every factor ships the number it was derived from.

If an AI service is ever added

The shape this report expected is a reasonable one. To make it real, four things would have to land together — this section is the acceptance list:

  1. Keys in ConfigKeys (Shared). The codebase forbids magic config strings, so an Ai section belongs there beside GitHub, with the secret itself in Key Vault under the existing PrefixKeyVaultSecretManager convention and never in appsettings*.json.
  2. Its own vertical slice under API/Features/. Slices may not reference each other; anything two slices need (as ownership checking did) moves to Auth/ or Shared rather than being copied.
  3. A [JsonSerializable] entry in AppJsonSerializerContext for every wire type. Trimming is on for the WASM client and the reflection resolver is deliberately unreachable — a missing entry fails at runtime in the browser, not at build.
  4. A named HttpClient with AddStandardResilienceHandler, matching GitHubClient: rate limiter → total timeout → retry → circuit breaker → attempt timeout. A provider outage must degrade one feature, not the analysis pipeline.

Only then would the matrix above have rows, and only then would a per-token rate be anything other than invented.
