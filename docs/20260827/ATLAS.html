System topology

One deployable. The API project serves the WebAssembly client out of its own wwwroot, so there is no CORS surface, no second host, and no origin mismatch to reason about.

Client

Blazor WASM, trimmed, Radzen components. Depends on .Shared only and talks to the server over HTTP plus one SignalR hub.

10 routes · trimming ON
API

Minimal API in eleven vertical slices. Each slice owns its endpoints, commands and handlers; the composition root is the only thing allowed to see all of them.

28 endpoints · MediatR handlers
Shared

DTOs, domain models, strongly-typed ids and validators. A leaf assembly — it references no other project, which is what lets both sides depend on it.

LEAF · no project refs
Storage

Azure Table Storage, four tables, no migrations. Azurite in development, managed identity in Azure.

4 tables · single-partition reads
The boundary that does the work

Slices must not reference each other. GlobalUsings.cs deliberately omits Features.*, so cross-slice coupling needs an explicit using that a reviewer can see. Anything genuinely shared moves to .Shared or to Auth/ — which is exactly why the repository-ownership guard lives in Auth and not in whichever slice needed it first.

02

Access & routes

One provider, one role, and a default of deny. There is no permission matrix to administer here — the only authorization question this system asks is whether the caller owns the row they named.

Who can sign in

GitHub, and nothing else. Microsoft/Entra was removed on purpose: that principal carries no GitHub credential, so it could sign in and then read nothing.

scopes: user:email read:user repo
What a session is

A cookie — HttpOnly, SameSite=Lax, seven-day sliding expiry. Lax rather than Strict because a Strict cookie is withheld on the post-OAuth landing redirect and the user loops forever on “pick an account”.

PoRepoLineTracker.Auth
What roles exist

None in Production. Dev and test runs can send X-Fake-Roles, and registering that handler in Production is a deliberate startup crash.

1 role: the signed-in owner
What a write costs

Both halves of an antiforgery pair: the cookie from the token endpoint plus the same value echoed as a header. Missing either is a 400.

X-CSRF-TOKEN

Steps 7 and 9 are the two that fail quietly when misconfigured — an unreachable store logs a warning and issues a temporary id; a missing token turns every write into a 400.

The four postures

  • Anonymous by declaration — /auth/*, /health, the antiforgery token, the SPA shell. Each opts out explicitly with AllowAnonymous().
  • Authenticated by fallback — everything else. A new endpoint added without any authorization metadata fails closed, not open.
  • Authenticated and owned — any route taking a repository id. RepositoryOwnership.AuthorizeAsync returns 404 for a missing id and 403 for someone else’s, and logs the attempt.
  • Authenticated and CSRF-paired — every state-changing method under /api.
Cookie hardening keys on HTTPS, not the environment name

Security:RequireSecureCookies decides whether the antiforgery cookie gets __Host- and Secure. A __Host- cookie without Secure is rejected by browsers; one with Secure never comes back over http. Either way every write fails while reads look fine — which is why the integration tier, running as environment Test over plain HTTP, opts out explicitly.

Denial payloads

Four refusals, four shapes. A client that branches on prose will break; branch on the status code, and on code where one is present.

401 — no session, or the session expired.
    The cookie handler short-circuits for /api rather than redirecting, because a
    cross-origin 302 to github.com surfaces in the browser as a CORS error.
HTTP/1.1 401 Unauthorized          // empty body

403 — authenticated, but the repository belongs to someone else. Logged as an IDOR attempt.
HTTP/1.1 403 Forbidden             // empty body

404 — the repository id does not exist. A plain string body, not ErrorResponse.
HTTP/1.1 404 Not Found
"Repository 0f0e…c1 not found."

404 — no API route claimed this path (GET only). ApiNotFoundMiddleware.
HTTP/1.1 404 Not Found
{
  "title":  "No such route",
  "detail": "GET /api/typo is not an API route on this server.",
  "code":   "route_not_found",
  "status": 404
}

400 — antiforgery. Deliberately says nothing about which half was missing.
500 — unhandled. application/problem+json, RFC 7807; traceId/stackTrace in Development only.
A known, deliberate limit

ApiNotFoundMiddleware covers GET. An unknown /api path reached by POST, PUT or DELETE still answers 401, because those verbs resolve past the SPA fallback before the middleware runs and the authorization challenge wins. The alternative — a catch-all endpoint covering every verb — was tried and reverted: it became a routing candidate beside the real routes and won some of them, so POST /api/repositories/bulk resolved to the catch-all, passed authorization because a catch-all must be anonymous, and returned 400 from the antiforgery gate instead of the 401 it owed. A bad error message on a route that does not exist beats a wrong outcome on one that does.

The workflow that matters

Adding repositories and analysing them is the one journey the whole system exists to serve. Everything else reads what this produces.

1 · Pick

The user signs in, and the app lists their GitHub repositories using their own token. Selection happens client-side.

GET /api/github/user-repositories
2 · Add

One bulk write, never one-at-a-time. /bulk dedupes; the single-add route was removed precisely because it did not.

POST /api/repositories/bulk
3 · Analyse

A background job clones, replays history, counts lines per commit, and reports each step. Four steps, live frames.

hub: /hubs/analysis
4 · Read

Charts, contributor share, code health, insights and the year recap all read stored commit rows. No further GitHub traffic.

Why the extensions list is replaced rather than appended to

Publish serialises the frame on a fire-and-forget task while the analysis loop keeps reporting. Appending to Extensions in place would throw mid-serialization, so the loop hands over a fresh list each time and the serializer always sees one complete snapshot or another.

Two performance rules the loop depends on

  • Line counting is memoised on git object ids. Trees are content-addressed, so an unchanged directory between two commits is one dictionary lookup rather than a recursive walk. The memo is keyed on object id and path, dropped when the counted-extension set changes, and CountLinesInCommitAsync returns a copy — a caller mutating a memoised instance would poison every later commit sharing that tree.
  • Never add a per-item storage lookup that a loop will call. CommitExistsAsync was removed for this: a point read per SHA meant a 4,000-commit repository paid 4,000 round-trips to answer what one whole-repository read already returns. The handler pre-loads that set and looks SHAs up in memory.
04

What the numbers mean

Three of this system’s figures look like they mean something other than what they measure. Getting these wrong produces plausible, confident, wrong dashboards.

TotalLines is a snapshot

Every commit row carries the whole repository’s line count at that commit — not a delta. Current size is the value on the newest commit, never a sum across commits.

RepositoryTotals, in .Shared
Contributor share is weighted

By lines added, not averaged per commit. A one-line commit and a 2,000-line refactor are not the same event.

GetContributorStatsQuery
Language drift is share

A file type’s share can grow while the type itself shrinks — everything else shrank faster. A line-count delta cannot show that.

the recap’s one non-obvious figure
Say what it is, on the card, not in a tooltip

The ranking is the reliable part; the absolute number is a guide. Two design decisions keep it honest: measuring and judging are separate types — CodeMetricsAnalyzer counts, CodeHealthScoring judges, so re-weighting the report cannot change what was counted. And markup is judged on its own nesting band: nested components are not a smell, and scoring .razor against the code band gave this repository’s own markup a 48 against 94 for its C#, which is a fact about the file format, not the code.

Tier 2 · Architectural

What gets counted, and what gets pruned

  • Vendored third-party code is excluded — and one rule does it by content, not name. A directory is pruned when its immediate children include two or more repository-root markers (LICENSE*, .github, .gitmodules, CODEOWNERS, …). That is another project copied in, whatever folder name the author gave it. The case it was written for was Unity’s ml-agents vendored under Training/, where a name-based rule left roughly 78% of the repository’s counted lines as third-party.
  • Comment syntax is configured per language family, and CSS is not C. Plain .css has no line-comment form — only /* */. Registering it with // truncated every line from its first //, so url(https://…) lost its tail and a line holding nothing else counted as blank. .scss and .less do have //, which is exactly why they cannot share an entry with .css; .razor uses @* *@ and HTML comments.
  • Filter changes only affect new analysis. Stored counts need a re-analyze — nothing retroactively re-prunes history.

Both the counter that discards comments and the analyzer that counts them read the same CommentSyntax table. Two copies would drift, and both sides would go on producing plausible numbers.

Signals & gates

What the running system tells you, and what has to be true before it ships.

Unit tests alone are not enough before committing

They pass against changes that break the whole integration tier. Composition-root changes in particular are invisible to the unit tier and load-bearing for every integration test. Run Unit and Integration at minimum. Note too that TreatWarningsAsErrors is on: a warning fails the build, and a running app locks it — stop the process before rebuilding.
