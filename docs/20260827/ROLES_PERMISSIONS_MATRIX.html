Tier 1 — Executive

Tier 1Thirty seconds:

Authorization is deny-by-default. A global FallbackPolicy requires an authenticated user on every endpoint that carries no authorization metadata of its own, so a new endpoint added without a RequireAuthorization() call fails closed rather than open. Only five endpoints opt out, each for a stated reason. There are no roles and no policies: the only authorization question beyond “are you signed in” is “do you own this repository”, and one shared guard answers it for every route that takes a repository id.

The two facts that carry the model

1. FallbackPolicy = RequireAuthenticatedUser() means forgetting a guard produces a 401, not a leak.
2. Auth/RepositoryOwnership.AuthorizeAsync is the single implementation of the ownership check. It lives in Auth/ rather than in a slice precisely so the second slice that needed it could not copy it — a copied authorization check fails quietly, and the symptom is a route serving another user's data rather than a broken build.

Tier 2 — Architectural

Tier 2Four gates decide every request, in this order. Three of them are middleware and one is per-endpoint code, and the ordering between them is deliberate.

Principals

P1 Anonymous

No credential. Reaches the login page, the health probe, the antiforgery token endpoint, the OAuth callback and the Blazor shell. Everything else answers 401 (API) or redirects (page).

P2 GitHub user — owner

Cookie PoRepoLineTracker.Auth, issued after GitHub OAuth. Carries a UserId claim added in OnCreatingTicket. Owns the repository named in the route. Full access to their own data.

P3 GitHub user — non-owner

Identical credential to P2, different UserId. Authenticated everywhere, but every repository-scoped route answers 403 and logs an IDOR warning naming both user ids.

P4 Header principal

X-Fake-User (GUID verbatim; any other string hashed to a stable GUID) plus optional X-Fake-Roles. Handled by FakeAuthHandler. Registered only outside Production — ThrowIfProduction makes a Production registration a startup crash rather than a silent bypass. There is no dev-login route.

P5 Infrastructure probe

Azure's health probe and the post-deploy smoke test. Credential-less by necessity. Reaches /health only; /diag requires authentication despite being a diagnostics surface.

Roles

X-Fake-Roles can attach role claims for a test, but no endpoint reads one. There is no RequireRole, no named policy, and no admin tier anywhere in the API. Authorization is authentication plus ownership.

The fallback policy

// Extensions/AuthServiceExtensions.cs
// Server-side FallbackPolicy: every endpoint that carries no authorization metadata of its own
// is authenticated by default. Endpoints that must stay public opt out explicitly with
// .AllowAnonymous(). Deny-by-default means a new endpoint added without a
// RequireAuthorization() call fails closed, not open.
services.AddAuthorization(options =>
{
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();
});

The API-vs-page split on denial

An unauthenticated /api call must not be answered with a cross-origin redirect to GitHub — the browser reports that as a CORS error, which tells the developer nothing. Both handlers short-circuit the prefix instead:

// Cookie scheme
options.Events.OnRedirectToLogin = context =>
{
    if (context.Request.Path.StartsWithSegments("/api"))
    {
        context.Response.StatusCode = StatusCodes.Status401Unauthorized;
        return Task.CompletedTask;
    }
    context.Response.Redirect(context.RedirectUri);
    return Task.CompletedTask;
};

// GitHub scheme - same rule, so an XHR never gets a 302 to github.com
options.Events.OnRedirectToAuthorizationEndpoint = context => { /* identical */ };

The ownership guard

// Auth/RepositoryOwnership.cs
public static async Task<(GitHubRepository? Repository, IResult? Error)> AuthorizeAsync(
    IRepositoryDataService repoDataService, RepositoryId repositoryId, UserId userId, string action)
{
    var existing = await repoDataService.GetRepositoryByIdAsync(repositoryId);
    if (existing == null)
        return (null, Results.NotFound($"Repository {repositoryId} not found."));

    if (existing.UserId != userId)
    {
        Log.Warning("IDOR attempt: user {UserId} tried to {Action} repo {RepositoryId} owned by {OwnerId}",
                    userId, action, repositoryId, existing.UserId);
        return (null, Results.Forbid());
    }

    return (existing, null);
}

The 404-vs-403 distinction is deliberate: a caller who owns nothing learns only that the id is not theirs, and the attempt is logged with both user ids and the verb phrase the call site supplied (“read linehistory for”, “reanalyze”, “read analysis-progress for”).

The header-driven scheme, and its guardrail

// Extensions/AuthServiceExtensions.cs
var useFakeAuth = !environment.IsProduction();
if (useFakeAuth)
{
    FakeAuthHandler.ThrowIfProduction(environment);   // startup crash, not a silent bypass
    services.AddAuthentication()
        .AddScheme<AuthenticationSchemeOptions, FakeAuthHandler>(FakeAuthHandler.SchemeName, _ => { })
        .AddPolicyScheme(SmartAuthScheme, SmartAuthScheme, options =>
        {
            options.ForwardDefaultSelector = context =>
                context.Request.Headers.ContainsKey(FakeAuthHandler.UserHeader)
                    ? FakeAuthHandler.SchemeName
                    : CookieAuthenticationDefaults.AuthenticationScheme;
        });
}

Selecting the scheme here rather than naming schemes on the authorization policies leaves FallbackPolicy scheme-agnostic, so it keeps working under any DefaultScheme. A request with no X-Fake-User header returns NoResult rather than a failure, so the cookie and OAuth schemes still get their turn and anonymous endpoints behave normally.

The SignalR hub

[Authorize]
public sealed class AnalysisHub : Hub
{
    public static string GroupFor(UserId userId) => $"user:{userId}";

    public override async Task OnConnectedAsync()
    {
        if (Context.User is not null && Context.User.TryGetUserId(out var userId))
            await Groups.AddToGroupAsync(Context.ConnectionId, GroupFor(userId));
        else
        {
            // [Authorize] guarantees an identity, but not that it carries the claim this app keys
            // on. Aborting is the safe reading: leaving the connection open would produce a client
            // that looks connected and silently receives nothing.
            Context.Abort();
            return;
        }
        await base.OnConnectedAsync();
    }
}

The hub is mounted at /hubs/analysis, deliberately outside /api: the antiforgery middleware validates every unsafe method under that prefix, and the SignalR negotiate handshake is a POST carrying no CSRF token. It is not relying on the prefix for protection — it is [Authorize] and scopes every connection to a per-user group. Progress frames go to Clients.Group("user:{id}"), and a job with no recorded owner is not broadcast at all rather than broadcast to everyone, since guessing would leak one user's repository names to another.

Unrouted /api paths answer before authentication

One gate deliberately runs ahead of authentication: ApiNotFoundMiddleware, registered after routing but before UseAuthentication/UseAuthorization. An /api path that matched no route — or matched only the SPA shell fallback — is a 404 regardless of who is asking, and letting the FallbackPolicy answer 401 first would make a typo indistinguishable from an expired session.

private static bool IsUnroutedApiRequest(HttpContext context)
{
    if (!context.Request.Path.StartsWithSegments("/api", StringComparison.OrdinalIgnoreCase))
        return false;

    var endpoint = context.GetEndpoint();
    return endpoint is null || endpoint.Metadata.GetMetadata<SpaFallbackAttribute>() is not null;
}

This does not weaken any guard. It cannot shadow a real route, because it is not an endpoint — and that is precisely why it is middleware. A MapFallback("/api/{**rest}") endpoint was tried first and reverted: it became a routing candidate beside the real routes and won for some of them, so POST /api/repositories/bulk matched the catch-all rather than the bulk endpoint. Because such a catch-all must be anonymous, an unauthenticated write then sailed through authorization and was refused by the antiforgery gate with 400 instead of the 401 it should have received.

Documented scope limit

This covers GET, not every verb. An unknown /api path reached by GET answers 404; the same path reached by POST/PUT/DELETE still answers 401, because those verbs resolve to something other than the SPA fallback before this runs and the authorization challenge wins. Deliberate scope, not an oversight: a write to a route that does not exist being refused as unauthorized is a poor error message, while a write to a route that does exist being refused for the wrong reason is a bug.
